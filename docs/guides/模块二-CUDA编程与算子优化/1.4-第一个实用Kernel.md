## 1. 从 CPU 到 GPU：一个完整的开发流程

将计算任务从 CPU 搬到 GPU 就像把工作从一个能干的员工交给一支千人团队——你需要准备材料、分配任务、等待完成、收回成果。对应到 CUDA 编程，完整流程是：

```mermaid
graph LR
    A["1. 分配 GPU 内存"] --> B["2. CPU→GPU 传数据"]
    B --> C["3. 启动 Kernel"]
    C --> D["4. GPU→CPU 取结果"]
    D --> E["5. 释放 GPU 内存"]
```

每一步都有对应的 CUDA API：

| 步骤 | API | 说明 |
|------|-----|------|
| 分配 GPU 内存 | `cudaMalloc()` | 类似 CPU 的 `malloc()` |
| Host→Device 传输 | `cudaMemcpy(..., HostToDevice)` | CPU 数据拷贝到 GPU |
| 启动 Kernel | `kernel<<<grid, block>>>(args)` | GPU 并行执行 |
| Device→Host 传输 | `cudaMemcpy(..., DeviceToHost)` | 结果拷回 CPU |
| 释放 GPU 内存 | `cudaFree()` | 类似 CPU 的 `free()` |

## 2. 向量加法 Kernel 实现

向量加法是最简单的并行问题——每个元素的计算完全独立，天然适合 GPU。给定两个长度为 N 的向量 A 和 B，计算：

$$
C[i] = A[i] + B[i], \quad i = 0, 1, \ldots, N-1
$$

### 2.1 Kernel 函数

```cpp
__global__ void vectorAdd(const float* A, const float* B, float* C, int N) {
    // 计算全局线程索引
    int idx = blockIdx.x * blockDim.x + threadIdx.x;

    // 边界检查：防止越界访问
    if (idx < N) {
        C[idx] = A[idx] + B[idx];
    }
}
```

代码解析：
- `const float*`：A 和 B 是只读输入
- `int idx`：每个线程计算一个唯一的全局索引
- `if (idx < N)`：最后一个 Block 可能有多余线程，必须检查边界
- `C[idx] = A[idx] + B[idx]`：每个线程独立完成一个元素的加法

### 2.2 为什么需要边界检查

假设 N = 1000，Block 大小 = 256：
- 需要 Block 数 = $\lceil 1000/256 \rceil = 4$
- 总线程数 = 4 × 256 = 1024
- 多出 24 个线程的索引为 1000~1023，超出数组范围

没有 `if (idx < N)` 检查，这些线程会访问非法内存地址，导致未定义行为或程序崩溃。

## 3. 主机端完整代码

### 3.1 内存管理

```cpp
#include <cstdio>
#include <cstdlib>
#include <cuda_runtime.h>

int main() {
    int N = 1 << 20;  // 约 100 万个元素
    size_t size = N * sizeof(float);

    // 1. 分配主机内存
    float* h_A = (float*)malloc(size);
    float* h_B = (float*)malloc(size);
    float* h_C = (float*)malloc(size);

    // 初始化输入数据
    for (int i = 0; i < N; i++) {
        h_A[i] = (float)i;
        h_B[i] = (float)(i * 2);
    }

    // 2. 分配设备内存
    float *d_A, *d_B, *d_C;
    cudaMalloc(&d_A, size);
    cudaMalloc(&d_B, size);
    cudaMalloc(&d_C, size);

    // 3. 将输入数据从 Host 拷贝到 Device
    cudaMemcpy(d_A, h_A, size, cudaMemcpyHostToDevice);
    cudaMemcpy(d_B, h_B, size, cudaMemcpyHostToDevice);

    // 4. 配置并启动 Kernel
    int blockSize = 256;
    int gridSize = (N + blockSize - 1) / blockSize;
    vectorAdd<<<gridSize, blockSize>>>(d_A, d_B, d_C, N);

    // 5. 将结果从 Device 拷回 Host
    cudaMemcpy(h_C, d_C, size, cudaMemcpyDeviceToHost);

    // 6. 验证结果
    for (int i = 0; i < N; i++) {
        if (fabsf(h_C[i] - (h_A[i] + h_B[i])) > 1e-5f) {
            printf("Verification FAILED at index %d!\n", i);
            break;
        }
    }
    printf("Verification PASSED!\n");

    // 7. 释放内存
    cudaFree(d_A);
    cudaFree(d_B);
    cudaFree(d_C);
    free(h_A);
    free(h_B);
    free(h_C);

    return 0;
}
```

### 3.2 编译与运行

```bash
$ nvcc vectorAdd.cu -o vectorAdd
$ ./vectorAdd
Verification PASSED!
```

## 4. CUDA 错误检查

CUDA API 调用可能失败（内存不足、参数错误等），生产代码中必须检查每个调用的返回值。

### 4.1 宏定义

```cpp
#define CUDA_CHECK(call)                                                      \
    do {                                                                       \
        cudaError_t err = call;                                                \
        if (err != cudaSuccess) {                                              \
            fprintf(stderr, "CUDA error at %s:%d - %s\n",                     \
                    __FILE__, __LINE__, cudaGetErrorString(err));              \
            exit(EXIT_FAILURE);                                                \
        }                                                                      \
    } while (0)
```

### 4.2 使用方式

```cpp
CUDA_CHECK(cudaMalloc(&d_A, size));
CUDA_CHECK(cudaMemcpy(d_A, h_A, size, cudaMemcpyHostToDevice));

// Kernel 启动的错误检查需要两步
vectorAdd<<<gridSize, blockSize>>>(d_A, d_B, d_C, N);
CUDA_CHECK(cudaGetLastError());          // 检查启动参数是否正确
CUDA_CHECK(cudaDeviceSynchronize());     // 检查执行过程是否有错误
```

### 4.3 常见错误码

| 错误码 | 含义 | 常见原因 |
|--------|------|---------|
| `cudaErrorMemoryAllocation` | 内存分配失败 | 显存不足 |
| `cudaErrorInvalidValue` | 参数无效 | size=0 或空指针 |
| `cudaErrorInvalidConfiguration` | 启动配置无效 | Block 超过 1024 线程 |
| `cudaErrorIllegalAddress` | 非法内存访问 | 越界/野指针 |
| `cudaErrorLaunchTimeout` | Kernel 执行超时 | 死循环或计算量过大 |

💡 **提示**：开发阶段建议在每个 CUDA API 后都加上错误检查。发布时可以用编译宏控制，在 Release 模式下去掉检查开销。

## 5. 性能测量：CPU vs GPU

### 5.1 CPU 基线实现

```cpp
void vectorAddCPU(const float* A, const float* B, float* C, int N) {
    for (int i = 0; i < N; i++) {
        C[i] = A[i] + B[i];
    }
}
```

### 5.2 使用 CUDA Event 计时

CUDA Event 是 GPU 端精确计时的标准方法，精度达微秒级：

```cpp
cudaEvent_t start, stop;
cudaEventCreate(&start);
cudaEventCreate(&stop);

// 计时开始
cudaEventRecord(start);

// 要计时的操作
vectorAdd<<<gridSize, blockSize>>>(d_A, d_B, d_C, N);

// 计时结束
cudaEventRecord(stop);
cudaEventSynchronize(stop);

// 计算耗时
float milliseconds = 0;
cudaEventElapsedTime(&milliseconds, start, stop);
printf("GPU Kernel time: %.4f ms\n", milliseconds);

// 清理
cudaEventDestroy(start);
cudaEventDestroy(stop);
```

### 5.3 包含数据传输的端到端计时

```cpp
cudaEventRecord(start);

cudaMemcpy(d_A, h_A, size, cudaMemcpyHostToDevice);
cudaMemcpy(d_B, h_B, size, cudaMemcpyHostToDevice);
vectorAdd<<<gridSize, blockSize>>>(d_A, d_B, d_C, N);
cudaMemcpy(h_C, d_C, size, cudaMemcpyDeviceToHost);

cudaEventRecord(stop);
cudaEventSynchronize(stop);

float totalTime = 0;
cudaEventElapsedTime(&totalTime, start, stop);
printf("GPU total (with memcpy): %.4f ms\n", totalTime);
```

### 5.4 性能结果对比（参考值）

在 RTX 4090 上，N = $2^{24}$（约 1600 万元素）的典型结果：

| 📊 指标 | CPU (单核) | GPU (仅 Kernel) | GPU (含传输) |
|---------|-----------|-----------------|-------------|
| 耗时 | ~25 ms | ~0.3 ms | ~8 ms |
| 有效带宽 | ~5 GB/s | ~400 GB/s | ~15 GB/s |

⚠️ **注意**：向量加法是**内存密集型**操作（每个元素只做 1 次加法但需要读 2 个 float、写 1 个 float）。包含数据传输时，PCIe 带宽成为瓶颈。GPU 的优势在数据已经在显存上时最明显。

**实测结果**（RTX 5060 Laptop GPU，WSL2 + CUDA 13，N = 2^24，2026-11）：

| 📊 指标 | CPU (单核) | GPU (仅 Kernel) | GPU (含传输) |
|---------|-----------|-----------------|-------------|
| 耗时 | 80.5 ms | 1.91 ms | 193.6 ms |
| 加速比 | — | **42.2×** | **0.4×** |
| 有效带宽 | — | 105.4 GB/s（峰值 27%） | 传输等效 ~0.67 GB/s |

三个数字**定性符合预期、定量被压低**——42× 加速和"PCIe 瓶颈"的结论都成立，但带宽和传输时间偏离典型值，原因在 7.2 / 7.3 的实测分析里逐条拆解。

## 6. 完整可运行代码

将以上所有部分整合为一个完整的、可直接编译运行的程序：

```cpp
#include <cstdio>
#include <cstdlib>
#include <cmath>
#include <chrono>
#include <cuda_runtime.h>

// 错误检查宏
#define CUDA_CHECK(call)                                                      \
    do {                                                                       \
        cudaError_t err = call;                                                \
        if (err != cudaSuccess) {                                              \
            fprintf(stderr, "CUDA error at %s:%d - %s\n",                     \
                    __FILE__, __LINE__, cudaGetErrorString(err));              \
            exit(EXIT_FAILURE);                                                \
        }                                                                      \
    } while (0)

// GPU Kernel
__global__ void vectorAdd(const float* A, const float* B, float* C, int N) {
    int idx = blockIdx.x * blockDim.x + threadIdx.x;
    if (idx < N) {
        C[idx] = A[idx] + B[idx];
    }
}

// CPU 基线
void vectorAddCPU(const float* A, const float* B, float* C, int N) {
    for (int i = 0; i < N; i++) {
        C[i] = A[i] + B[i];
    }
}

int main() {
    const int N = 1 << 24;  // 约 1600 万元素
    const size_t size = N * sizeof(float);
    printf("Vector size: %d elements (%.1f MB)\n", N, size / (1024.0 * 1024.0));

    // ========== 分配主机内存 ==========
    float* h_A = (float*)malloc(size);
    float* h_B = (float*)malloc(size);
    float* h_C_cpu = (float*)malloc(size);
    float* h_C_gpu = (float*)malloc(size);

    // 初始化数据
    for (int i = 0; i < N; i++) {
        h_A[i] = sinf(i * 0.001f);
        h_B[i] = cosf(i * 0.001f);
    }

    // ========== CPU 计算 ==========
    auto cpu_start = std::chrono::high_resolution_clock::now();
    vectorAddCPU(h_A, h_B, h_C_cpu, N);
    auto cpu_end = std::chrono::high_resolution_clock::now();
    float cpu_ms = std::chrono::duration<float, std::milli>(cpu_end - cpu_start).count();
    printf("CPU time: %.4f ms\n", cpu_ms);

    // ========== GPU 计算 ==========
    float *d_A, *d_B, *d_C;
    CUDA_CHECK(cudaMalloc(&d_A, size));
    CUDA_CHECK(cudaMalloc(&d_B, size));
    CUDA_CHECK(cudaMalloc(&d_C, size));

    // 创建 CUDA Event 计时器
    cudaEvent_t start, stop, kernel_start, kernel_stop;
    cudaEventCreate(&start);
    cudaEventCreate(&stop);
    cudaEventCreate(&kernel_start);
    cudaEventCreate(&kernel_stop);

    // 端到端计时（含传输）
    cudaEventRecord(start);

    CUDA_CHECK(cudaMemcpy(d_A, h_A, size, cudaMemcpyHostToDevice));
    CUDA_CHECK(cudaMemcpy(d_B, h_B, size, cudaMemcpyHostToDevice));

    int blockSize = 256;
    int gridSize = (N + blockSize - 1) / blockSize;

    // 仅 Kernel 计时
    cudaEventRecord(kernel_start);
    vectorAdd<<<gridSize, blockSize>>>(d_A, d_B, d_C, N);
    cudaEventRecord(kernel_stop);

    CUDA_CHECK(cudaGetLastError());
    CUDA_CHECK(cudaMemcpy(h_C_gpu, d_C, size, cudaMemcpyDeviceToHost));

    cudaEventRecord(stop);
    cudaEventSynchronize(stop);

    float gpu_total_ms = 0, kernel_ms = 0;
    cudaEventElapsedTime(&gpu_total_ms, start, stop);
    cudaEventElapsedTime(&kernel_ms, kernel_start, kernel_stop);

    printf("GPU kernel time: %.4f ms\n", kernel_ms);
    printf("GPU total time (with memcpy): %.4f ms\n", gpu_total_ms);
    printf("Speedup (kernel only): %.1fx\n", cpu_ms / kernel_ms);
    printf("Speedup (end-to-end): %.1fx\n", cpu_ms / gpu_total_ms);

    // ========== 结果验证 ==========
    int errors = 0;
    for (int i = 0; i < N; i++) {
        if (fabsf(h_C_gpu[i] - h_C_cpu[i]) > 1e-5f) {
            if (errors < 5) {
                printf("Mismatch at %d: CPU=%.6f, GPU=%.6f\n",
                       i, h_C_cpu[i], h_C_gpu[i]);
            }
            errors++;
        }
    }
    if (errors == 0) {
        printf("Verification PASSED!\n");
    } else {
        printf("Verification FAILED: %d mismatches\n", errors);
    }

    // ========== 计算有效带宽 ==========
    // 向量加法读 2 个 float、写 1 个 float = 12 bytes/element
    float bandwidth_gb = (3.0f * size) / (kernel_ms * 1e-3f) / 1e9f;
    printf("Effective bandwidth: %.1f GB/s\n", bandwidth_gb);

    // ========== 清理 ==========
    cudaEventDestroy(start);
    cudaEventDestroy(stop);
    cudaEventDestroy(kernel_start);
    cudaEventDestroy(kernel_stop);
    CUDA_CHECK(cudaFree(d_A));
    CUDA_CHECK(cudaFree(d_B));
    CUDA_CHECK(cudaFree(d_C));
    free(h_A);
    free(h_B);
    free(h_C_cpu);
    free(h_C_gpu);

    return 0;
}
```

## 7. 性能分析与讨论

### 7.1 向量加法的算术强度

**算术强度**（Arithmetic Intensity）= 计算量 / 内存访问量：

$$
\text{AI} = \frac{\text{FLOPs}}{\text{Bytes}} = \frac{1 \text{ FLOP}}{12 \text{ Bytes}} \approx 0.083 \text{ FLOP/Byte}
$$

这个值极低，说明向量加法是**典型的内存密集型**操作，性能受限于内存带宽而非计算能力。

### 7.2 带宽利用率分析

如果 Kernel 时间为 0.3 ms，处理 $3 \times 2^{24} \times 4$ Bytes = 201 MB 数据：

$$
\text{有效带宽} = \frac{201 \text{ MB}}{0.3 \text{ ms}} \approx 670 \text{ GB/s}
$$

对比 RTX 4090 的理论峰值带宽 1008 GB/s，利用率约 66%——对于如此简单的 Kernel 来说已经不错。

**实测分析：为什么 5060 Laptop 上只有 105.4 GB/s（27% 峰值）？**

差距主因不是 Kernel 写得差，而是**单次测量没有预热**：GPU 空闲时内存时钟压在低功耗档，1.9 ms 的 Kernel 太短，时钟还没爬升到满频就跑完了。对照 1.3 章 3.5 节的合并访问实验——同一张卡，"预热 1 次 + 跑 5 次取最小"的测法能到 346 GB/s（90% 峰值）。

📌 **结论：凡是 bandwidth benchmark，永远先预热再计时，并取多次运行的最优值。** 单次裸测的数据可以用来讲方法论，不能用来评估硬件。

### 7.3 PCIe 传输的开销

| 📊 环节 | 典型耗时 | 占比 |
|---------|---------|------|
| H2D 传输 (64MB × 2) | ~5 ms | ~60% |
| Kernel 执行 | ~0.3 ms | ~4% |
| D2H 传输 (64MB) | ~3 ms | ~36% |

📌 **关键点**：对于简单的逐元素操作，数据传输往往是主要瓶颈。实际应用中应尽量让数据"留在 GPU 上"——多个 Kernel 串联处理同一批数据，避免反复搬运。

**实测分析：为什么实测传输只有 ~0.67 GB/s？**

5060 Laptop + WSL 实测中，三次传输共 128 MB 耗时 ~191.7 ms（193.6 − 1.91），等效带宽仅 ~0.67 GB/s，比典型 PCIe 的 10+ GB/s 慢一个数量级。三个原因叠加：

1. **Pageable 内存**：host 内存用 `malloc` 分配，`cudaMemcpy` 要先拷进驱动的中转缓冲再走 DMA；若用 `cudaMallocHost()`（Pinned Memory，见 8.4 练习）可直接 DMA，快数倍
2. **WSL 虚拟化开销**：WSL 的拷贝路径经过 `/dev/dxg` 虚拟设备，本身就比原生 Linux 慢
3. **首次触摸缺页**：`h_C_gpu` 在 D2H 拷回时才第一次被 CPU 写入，64 MB 的缺页中断全部计入了端到端时间

所以端到端 0.4× 的"PCIe 教训"依然成立，只是绝对值被这三件事进一步放大。原生 Linux + pinned 内存下，同样的实验传输耗时应回落到 ~15 ms 量级。

### 7.4 何时值得用 GPU

| 场景 | CPU 更好 | GPU 更好 |
|------|---------|---------|
| 数据量小（< 10K 元素） | ✅ | ❌ |
| 单次简单操作 + 数据不在 GPU | ✅ | ❌ |
| 大数据 + 数据已在 GPU | ❌ | ✅ |
| 大数据 + 多步串联计算 | ❌ | ✅ |
| 计算密集型（如矩阵乘法） | ❌ | ✅ |

## 8. 进阶练习

完成向量加法后，尝试以下练习来巩固所学：

### 8.1 练习 1：向量点积

实现两个向量的点积 $\text{result} = \sum_{i=0}^{N-1} A[i] \times B[i]$。

提示：这需要**规约**（Reduction）——每个线程计算部分乘积，然后在 Block 内用共享内存累加。

#### 延伸实验：为什么 GPU 算出来的点积反而更准

把点积写成"每 Block 树形规约 + 跨 Block `atomicAdd`"之后，扫一遍不同规模，会撞上一个反直觉的现象：**随着 N 增大，GPU 与 CPU 的结果开始不一致，而错的是 CPU。**

实验代码见 `experiments/dotProduct_timing.cu`（CPU 用 `std::chrono` 单次计时，GPU 用 CUDA Event 预热后取 10 次最优）。输入全部填 `1.0`，所以点积的真值就是 N，肉眼即可校验。

**实测结果**（RTX 5060 Laptop，WSL + CUDA 13，2026-11）：

| N | 数据量 | CPU 耗时 | GPU 耗时 | 加速比 | GPU 带宽 | 与 CPU 的相对误差 |
|---|--------|---------|---------|--------|---------|-----------------|
| 1M (1048576) | 8 MB | 0.735 ms | 0.035 ms | 20.7× | 236.8 GB/s | 0 |
| 2M | 16 MB | 1.472 ms | 0.066 ms | 22.3× | 254.0 GB/s | 0 |
| 4M | 32 MB | 5.702 ms | 0.121 ms | 47.0× | 276.7 GB/s | 0 |
| 8M | 64 MB | 8.195 ms | 0.251 ms | 32.7× | 267.8 GB/s | 0 |
| 16M | 128 MB | 11.532 ms | 0.469 ms | 24.6× | 286.4 GB/s | 0 |
| 32M | 256 MB | 30.437 ms | 0.935 ms | 32.5× | 287.0 GB/s | **1.0** |
| 64M | 512 MB | 77.929 ms | 1.850 ms | 42.1× | 290.2 GB/s | **3.0** |

误差不是慢慢涨的，而是**从 N=32M 起突然跳到整数 1.0、3.0**——这种"整整齐齐"的数字不可能是舍入噪声，只能是系统性停滞。

**原因：CPU 的 float 串行累加在 $2^{24}$ 处彻底饱和**

`float` 只有 24 位有效精度（1 位符号 + 8 位指数 + 23 位尾数）。它在任何量级上只能铺开约 1677 万个刻度，数值越大刻度越稀：

```
[2^23, 2^24)  ulp = 1        ← 整数都能精确表示
[2^24, 2^25)  ulp = 2        ← 只能表示偶数
[2^25, 2^26)  ulp = 4        ← 只能表示 4 的倍数
```

CPU 那版是严格串行的累加，`sum` 涨到 $2^{24}=16777216$ 之后，再加 1 需要落在 $2^{24}+1$ 这个位置——那里没有对应的 float，它正好是 $2^{24}$ 和 $2^{24}+2$ 的中点。IEEE 754 的中点舍入规则是 ties-to-even，于是舍回 $2^{24}$。**加法执行了，值没变；而且这个停滞是永久的，再加一百万次也一样。**

代入数字验证，与实测完全吻合：

- N=32M 时真值 33554432，CPU 停在 16777216，误差 $=(33554432-16777216)/16777216=1.0$
- N=64M 时真值 67108864，CPU 还是 16777216，误差 $=3.0$

**GPU 为什么没这个问题**

误差的真正来源不是"加的次数多"，而是**两个加数数量级悬殊**。GPU 那版每一层都在加同量级的东西：

1. 块内树形规约：加的两个数都是 1，或都是 2、4、8……同量级且都是小整数，全部精确
2. 每个 Block 的结果恰好是 256，一个整数
3. 跨 Block `atomicAdd`：和值涨到 3.3e7 时 ulp = 4，涨到 6.7e7 时 ulp = 8，而 **256 是 4 和 8 的整数倍**，每次加都精确落在刻度上，一分不丢

所以 GPU 的结果精确等于 N。这就是 pairwise summation（成对求和）的性质：**误差按 $O(\log N)$ 累积，而不是串行的 $O(N)$**。同样用 float，树形结构的精度反而高于朴素串行循环——NumPy 的 `np.sum`、Julia 的 `sum` 默认就这么做。

**另外两个值得注意的现象**

- **GPU 带宽只有 290 GB/s（峰值的 75%）**，低于 3.5 节合并访问实验的 346 GB/s（90%）。差额来自规约开销：每 256 个元素就要付 8 轮共享内存 + `__syncthreads` 的同步成本，再加一次 `atomicAdd`。优化方向是让每个线程先在寄存器里攒 4~8 个元素，再进块内规约——块数减到 1/4，同步开销摊薄到 1/4。
- **加速比忽高忽低（47× → 24.6× → 42.1×）不是 GPU 在抖**，而是 CPU 单次计时在抖：CPU 耗时 8.2 → 11.5 → 30.4 ms 完全不是两倍关系。CPU 端也应该跑 3 次取最优，否则加速比没有比较价值（这也是 7.2 节"benchmark 必须预热 + 取最优"的另一面）。

**三条通用对策**

| 手段 | 做法 | 适用场景 |
|------|------|---------|
| 换精度 | 累加用 `double`，误差上限从 $2^{-24}$ 降到 $2^{-53}$ | 精度敏感、性能不敏感（如 loss 计算） |
| 改顺序 | 两两配对 / 分块求和，永远加同量级 | GPU 天然如此；CPU 端写分块也能大幅改善 |
| 加补偿 | Kahan 求和：用 `c` 记录被舍入吞掉的差额，攒够后再加回 | 累加次数极多、单遍扫描、不能换 double |

💡 这个实验的价值在于：**它推翻的是"CPU 纯串行 = 更准确"的直觉**。判断浮点结果可信与否，看的是加法的组织方式，而不是跑在哪个硬件上。

### 8.2 练习 2：SAXPY

实现 SAXPY 操作：$Y[i] = \alpha \times X[i] + Y[i]$

这是 BLAS 的基础操作，比向量加法多一个标量乘法。

#### 延伸实验：SAXPY 的耗时与带宽

练习代码见 `experiments/saxpy.cu`（N = 2²⁴ = 16777216，a = 2.0，x/y 各 64 MB）。CPU 用 `std::chrono` 计时，GPU 用 CUDA Event 预热后取 10 次最优；两端按同一口径统计有效带宽——每元素访存 12 字节（读 x、读 y、写 y）。

**实测结果**（RTX 5060 Laptop，WSL + CUDA 13，2026-11）：

| 版本 | 耗时 | 吞吐 | 有效带宽 | 加速比 |
|------|------|------|---------|--------|
| CPU（单线程） | 15.041 ms | 1.12 G items/s | 13.4 GB/s | 1× |
| GPU | 0.603 ms | 27.84 G items/s | 334.0 GB/s | **25.0×** |

逐元素校验 `max|diff| = 0.000000`，PASS。

> 重跑会有 ~10% 抖动（CPU 13.4~15.0 ms、GPU 0.598~0.618 ms 都属正常，取决于时钟与系统负载），但「带宽比 ≈ 加速比」这个关系每次都成立——看关系比看单个数字可靠。

**核心结论：加速比 ≈ 带宽比**

334.0 / 13.4 ≈ 25，和实测加速比 25.0× 完全一致。这不是巧合：SAXPY 每个元素只做 1 次乘加，计算量极小，时间几乎全花在搬运 12 字节上；两边搬的字节数相同，于是

```
加速比 = t_CPU / t_GPU = BW_GPU / BW_CPU
```

这条等式只在**纯访存型（memory-bound）kernel** 上成立。换成 9.3 节的矩阵乘（计算密集型），加速比与带宽比就会脱钩，那时该看 GFLOPS 而不是 GB/s。GPU 的 334 GB/s 已达理论峰值 384 GB/s 的 **87%**，与 1.3 节 3.5 实验里"合并访问 346 GB/s（90%）"同一水平——说明 SAXPY 的读改写访存模式也是合并的。

对照 8.1 的点积：点积要走块内树形规约 + 跨块 atomicAdd，带宽只到 290 GB/s（75%）；SAXPY 没有规约，纯顺序读写，反而更能吃满带宽。同一个"每元素 12 字节"的口径下，**差别全在同步开销**。

**为什么 CPU 只有 13.4 GB/s**：单线程 + 128 MB 工作集远超 L3，全靠 DRAM 供给；笔记本 DDR5 理论带宽几十 GB/s，但单核能用到的本就有限，再叠加 WSL 虚拟化的访存开销。改成多线程/OpenMP 能明显提升，但那已不是本题重点。

**两个必须记住的坑**

1. **in-place 的计时陷阱**：`y` 既是输入又是输出，计时循环里重复跑 10 次会让 y 越滚越大。kernel 的工作量与数值无关，所以计时依然有效；但正确性校验前必须用 `cudaMemcpy` 把 y 重置回初值、只跑一次，否则比对的是"被加了 11 次"的结果。
2. **静默失败比报错更危险**：实验过程中曾出现"CPU/GPU 都 0.000 ms、加速比 3.6e38、`maxDiff=0 PASS`"的荒谬输出。根因是 Windows 显卡驱动更新后 WSL 虚拟机没重启，`/usr/lib/wsl/lib/libcuda.so` 与 CUDA 13 runtime 失配，所有 CUDA 调用返回 `CUDA driver version is insufficient for CUDA runtime version`，kernel 根本没执行——两边数组都没被改动，于是"结果一致"。另外 CPU 循环当时也是空的，被 `-O3` 直接优化掉，才有了 0.000 ms。

   修复只需在 Windows 侧执行 `wsl --shutdown` 再重进。**更根本的预防是给每个 CUDA 调用加错误检查**（本实验代码里的 `CHECK(call)` 宏）：驱动失效时直接打印错误退出，而不是让一个假 PASS 骗过你。凡是 benchmark 输出超出物理常识（带宽超过显存峰值、加速比是天文数字），先怀疑测量代码和错误码，而不是怀疑硬件。

### 8.3 练习 3：Grid-stride Loop 版本

将向量加法改为 Grid-stride loop 写法，启动固定数量的线程处理任意大小的数组：

```cpp
__global__ void vectorAddStride(const float* A, const float* B,
                                float* C, int N) {
    int idx = blockIdx.x * blockDim.x + threadIdx.x;
    int stride = blockDim.x * gridDim.x;
    for (int i = idx; i < N; i += stride) {
        C[i] = A[i] + B[i];
    }
}

// 启动时不再需要 gridSize = (N + 255) / 256
// 可以选择任意合理的 Grid 大小
vectorAddStride<<<128, 256>>>(d_A, d_B, d_C, N);
```

### 8.4 练习 4：异步传输与计算重叠

使用 CUDA Stream 让数据传输和计算并行执行：

```cpp
cudaStream_t stream;
cudaStreamCreate(&stream);

// 异步传输和计算可以重叠
cudaMemcpyAsync(d_A, h_A, size, cudaMemcpyHostToDevice, stream);
cudaMemcpyAsync(d_B, h_B, size, cudaMemcpyHostToDevice, stream);
vectorAdd<<<gridSize, blockSize, 0, stream>>>(d_A, d_B, d_C, N);
cudaMemcpyAsync(h_C, d_C, size, cudaMemcpyDeviceToHost, stream);

cudaStreamSynchronize(stream);
cudaStreamDestroy(stream);
```

💡 **提示**：要实现真正的重叠，主机端内存必须使用 `cudaMallocHost()`（Pinned Memory）分配。

## 📝 总结

通过向量加法这个完整案例，我们掌握了 CUDA 编程的核心流程：

1. **五步标准流程**：cudaMalloc → cudaMemcpy(H2D) → Kernel Launch → cudaMemcpy(D2H) → cudaFree
2. **Kernel 编写三要素**：全局索引计算 + 边界检查 + 并行计算
3. **错误检查**：用 `CUDA_CHECK` 宏包裹每个 API 调用
4. **性能度量**：CUDA Event 计时 + 有效带宽计算
5. **性能认知**：简单操作的瓶颈在内存传输，GPU 优势在数据驻留和计算密集场景

向量加法虽然简单，但它建立起了 CUDA 编程的完整框架。后续学习矩阵乘法、卷积、规约等高级 Kernel 时，都是在这个框架上增加复杂度。
